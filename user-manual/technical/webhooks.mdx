## Overview

Webhooks let you receive real-time notifications when specific events occur on the platform. When a configured event happens — such as an order completing or an attendee checking in — the platform sends an HTTP request to a URL you specify, containing details about what happened. This enables you to integrate the platform with external systems without polling for changes.

Common uses include:

- Syncing completed orders to a CRM or fulfilment system
- Triggering workflows in automation tools when events are created
- Recording attendee check-ins in an external access control system
- Tracking refunds and payouts in accounting software

<Note>
Webhooks are a premium feature. If webhooks are not available in your account, contact your account manager to enable them.
</Note>

## Webhook Events

The platform supports the following event types:

| Event | When it fires |
|-------|---------------|
| **Order completed** | When a new order is completed. |
| **Reservation Created** | When a new reservation is created. For payment link orders, this fires both when the reservation is first generated and again if the customer chooses a payment method that results in a reservation, such as invoice. |
| **Order failed** | When an order either expires or there is a payment failure during checkout. |
| **Order refunded** | When an order is refunded. |
| **Order refund failed** | When an order refund fails. |
| **New event** | When a new event is created. |
| **Attendee check in** | When an attendee checks into a zone or main entry. |
| **Attendee check out** | When an attendee checks out of a zone or main exit. |
| **Custom form submission** | Whenever a custom data capture form is submitted. |
| **Resale Payout** | When resale payouts are distributed to the original seller. |
| **Resale Payout Failed** | When a resale payout fails. |

### Attendee Check Out

<Tip>New in Release 47</Tip>

The **Attendee check out** webhook lets integrations react when an attendee is scanned **out** of an event. It fires whenever a scan-out is recorded — whether the attendee leaves a specific zone or the main **Entry** zone — making it the counterpart to **Attendee check in**.

Scan-outs are produced wherever in/out scanning is used: in/out zones, the default [Entry](/user-manual/event-management/access-control#the-default-entry-zone) zone (when set to an in/out [scan mode](/user-manual/event-management/access-control#scan-modes)), [auto scan-out](/user-manual/event-management/access-control#auto-scan-out) times, and out-direction scans sent through the [Admit Entry Tickets](/api-reference/access-control/admit-entry-tickets) API.

Each delivery contains a `scans` array. Every entry identifies the company, event, zone, customer, and item, along with the time the attendee was scanned out (`scannedAt`) and how long they spent in the zone (`visitDuration`, in seconds). See the [Webhook Reference](/webhook-reference) for the full payload.

## Creating a Webhook

To create a new webhook:

1. Navigate to **Webhooks** in the admin panel.
2. Click **Create webhook**.
3. Configure the webhook settings (see [Configuration](#configuration) below).
4. Save the webhook.

The webhook begins firing immediately for new events matching its type.

## Configuration

Each webhook has the following settings:

### Basic Settings

| Setting | Description |
|---------|-------------|
| **Name** | A descriptive name to identify this webhook in the list |
| **URL** | The endpoint that will receive the webhook requests |
| **HTTP Request Method** | The HTTP method used for the request (typically POST) |
| **Type** | The event type that triggers this webhook |

### Secret

Each webhook is signed with a shared secret, set in the **Secret** field when you create or edit it. A secret is required — the webhook cannot be saved without one. Click **Generate** to produce a new secret; it is copied to your clipboard at the same time, ready to paste into the application that will receive the calls.

The platform signs every payload with HMAC-SHA256 using this secret and sends the result in the **Signature** header. Checking that header is what proves a request came from us, rather than from anyone who happened to discover your endpoint URL.

<Note>
A new secret applies from the next delivery onwards. Update your receiving application at the same time you save the change, or verification will start failing on live events.
</Note>

#### Verifying the Signature

The **Signature** header holds a lowercase hexadecimal HMAC-SHA256 digest of the JSON request body, keyed with the webhook's secret. There is no prefix, version tag or timestamp in the value — the digest is the entire header.

<Warning>
Verification depends on there being a request body to hash. When **HTTP Request Method** is set to `GET`, the payload is sent as query string parameters and no body is sent, leaving nothing to verify against. Use `POST` wherever the signature matters.
</Warning>

The check is the same three steps in any language:

```
// 1. Read the raw request body — the exact bytes received, before parsing the JSON.
rawBody = request.rawBody()

// 2. Compute the expected digest using the value from the webhook's Secret field.
expected = hex(hmac_sha256(key: webhookSecret, message: rawBody))

// 3. Compare it against the header, in constant time.
if (not constant_time_equals(expected, request.header("Signature"))) {
    respond(401)
    return
}

// Only now is the payload safe to trust.
respond(200)
process_asynchronously(json_parse(rawBody))
```

<Warning>
Hash the raw body, not a re-serialised copy of the parsed payload. Re-encoding JSON changes key order, whitespace and character escaping, and any one of those produces a different digest — so the check fails on every delivery, even though the requests are genuine.
</Warning>

Three things commonly go wrong:

| Problem | What to do instead |
|---------|--------------------|
| Comparing the two values with a plain string equality check | Use a constant-time comparison — `hash_equals`, `crypto.timingSafeEqual`, `hmac.compare_digest` — so a failing check cannot be probed a character at a time. |
| Reading the body after the framework has parsed it | Many frameworks consume the request stream to build the parsed payload, leaving nothing to hash. Capture the raw body first, via middleware or your framework's raw-body option. |
| Verifying and processing before responding | Requests time out after 3 seconds. Verify, respond, then do the work asynchronously. |

<Note>
There is no timestamp header, so a valid signature on its own does not tell you whether a request is a replay. Deliveries are attempted up to three times, which means the same signed payload can legitimately arrive more than once for one event — key your processing on something stable in the payload, such as the order reference, and make it idempotent.
</Note>

<Note>
Test requests are signed exactly like real ones, so you can confirm your verification code works using the [test option](#testing-a-webhook) before a live event fires. The **Signature** value sent with any delivery is also listed under **Headers** on the call detail page — see [Monitoring Webhook Activity](#monitoring-webhook-activity).
</Note>

### Payload Settings

| Setting | Description |
|---------|-------------|
| **Includes** | Configure which related objects to include in the webhook payload. For order webhooks, this can include ticket details, customer information, billing address, and data capture responses. |
| **Order type** | For order-related webhooks, specify whether to trigger for all orders, resale orders only, or non-resale orders only. |

## Testing a Webhook

Before relying on a webhook in production, you can send a test request:

1. Navigate to the webhook's detail page.
2. Click the test option.
3. Optionally modify the test payload.
4. Send the test request.

The test sends a sample payload to your configured URL, allowing you to verify that your endpoint receives and processes the data correctly.

## Monitoring Webhook Activity

Each webhook's detail page shows a call history graph displaying successful and failed deliveries over time. This gives you a visual overview of webhook reliability.

To inspect an individual delivery:

1. Open the webhook's detail page.
2. Browse the call history.
3. Click on a specific call to view full details.

Each call record shows:

- The request URL, HTTP method, and payload sent
- The response status code, headers, and body received
- Whether the delivery was successful
- The number of attempts made
- Any error messages if the delivery failed

## Retry Behaviour

If a webhook delivery fails (due to a timeout, network error, or non-success HTTP status code), the platform retries automatically:

- **Maximum attempts**: 3
- **Backoff strategy**: Exponential — each retry waits longer than the previous one
- **Timeout**: Requests time out after 3 seconds

<Note>
If all retry attempts fail, the delivery is marked as permanently failed. The platform does not retry beyond the maximum attempt count. Check the call history regularly to identify persistent failures and verify that your endpoint is reachable.
</Note>

## Enabling and Disabling Webhooks

Webhooks can be temporarily disabled without deleting them:

- **Disable** a webhook to stop it from firing. The webhook configuration is preserved but no requests are sent.
- **Enable** a disabled webhook to resume delivery.

Events that occur while a webhook is disabled are not sent retroactively. This is useful when your receiving endpoint is undergoing maintenance or when you need to temporarily pause an integration.

## Managing Webhooks

From the webhooks list, you can:

| Action | Description |
|--------|-------------|
| **Edit** | Modify webhook settings, URL, or type |
| **Delete** | Remove a webhook. Deleted webhooks can be restored. |
| **Restore** | Recover a previously deleted webhook |
| **Enable / Disable** | Toggle webhook delivery on or off |

The webhooks list supports filtering by name, URL, HTTP method, type, and creation date.

## Webhook Payloads

Webhook payloads are sent as JSON. The top-level key indicates the event type (e.g. `order_completed`, `new_event`). The content varies by event type, but order-related webhooks typically include:

- **Company** — ID and name
- **Order** — ID, reference, total, amount paid, and timestamps
- **Currency** — Symbol and code
- **Customer** — ID, name, and email
- **Billing address** — Full address details
- **Items** — Grouped by type: tickets, season tickets, products, donations, fees, and fulfilment fees
- **Data capture** — Custom form responses associated with the order

The exact payload structure depends on the event type and your **Includes** configuration. For full payload examples, see the [Webhook Reference](/webhook-reference).
