## Overview

Most events scan attendees in with the [Access Control Pro](/mobile-apps/access-control-pro/introduction) app. This page is for when that does not fit: turnstiles and gate hardware, a scanning app of your own, or a venue system that already owns entry.

The same API the app uses is available to you. The main decision is which of two models you build against.

<Note>
Read [Access Control](/core-platform/event-management/access-control) first. Zones, scan modes, limits, capacity, eligible items, age restrictions and validity dates are configured per event and enforced by the platform — your integration inherits those rules rather than defining them.
</Note>

## Two Models, One Decision

| | Real-time zone scanning | Offline bulk sync |
|---|---|---|
| **Endpoint** | [Scan Zone](/api-reference/zones/scan-zone) | [Admit Entry Tickets](/api-reference/access-control/admit-entry-tickets) |
| **Needs connectivity at the moment of scanning** | Yes | No |
| **Zone rules enforced** | All of them, at scan time | Not at scan time |
| **Capacity checks** | Live | None |
| **In/out scanning** | Yes | Recorded, not validated |
| **Suits** | Turnstiles, staffed gates, zone-controlled areas | Festival fields, remote gates, unreliable networks |

**Where there is a network at the gate, use real-time zone scanning.** It is the model that enforces what the event was configured to enforce. Offline sync is for gates where connectivity cannot be relied on.

### Real-Time Zone Scanning

One call per scan, validated as it happens:

```
POST /v1/zones/scan
```

```json
{
  "barcodes": ["R6LXATTKDH"],
  "zoneId": "1",
  "scan": "auto",
  "uuid": "b2f1c3d4-..."
}
```

Every rule the zone was configured with is applied: eligible items, scan limits, capacity, age restrictions, validity dates, opening and closing times. A denied scan comes back with the reason, so your gate can display something specific rather than a generic failure.

| Field | Notes |
|-------|-------|
| `barcodes` | One or more. **All-or-nothing** — if any barcode is denied, none are admitted. |
| `nfcIds` | Paired NFC tags. Takes precedence over `barcodes` when both are sent. Also all-or-nothing. |
| `zoneId` | Which zone. Fetch the event's zones with [Retrieve Zones](/api-reference/zones/retrieve-zones). |
| `scan` | `in`, `out`, or `auto` to let the platform decide from the attendee's current state. |
| `uuid` | Idempotency key. A repeated `uuid` returns the previous successful response rather than scanning again. |
| `latitude`, `longitude` | Where the scan happened. Recorded against it. |
| `confirmed` | For zones with precision scanning: says these barcodes are the final choice, skipping the check for eligible child items. |
| `ignoreAgeRestrictions`, `ignoreCapacity` | Override, for a staffed gate with authority to let somebody through. |

<Warning>
Always send `uuid`. Gate hardware retries and networks drop mid-response, and a scan that succeeded but whose response you never saw looks identical to one that failed. Without an idempotency key a retry double-counts the attendee against a scan limit or a capacity.
</Warning>

### Checking Without Scanning

[Check Zone Item Eligibility](/api-reference/zones/check-zone-item-eligibility) answers "would this scan succeed?" and returns live statistics, without recording anything. It takes the same identifiers and the same overrides as a real scan.

Use it for a pre-flight display — a screen telling somebody they are in the wrong queue, or a staffed check before committing — rather than as a validation step before every scan.

Two calls per admission doubles your traffic against the [rate limit](/integrate/getting-access#rate-limits), and eligibility confirmed a moment ago is not eligibility now.

### Offline Bulk Sync

Where connectivity cannot be relied on, download the valid tickets in advance, validate locally, and upload the results when you have a network again.

<Steps>
  <Step title="Download the valid tickets">
    [Retrieve Entry Tickets](/api-reference/access-control/retrieve-entry-tickets) returns everything valid for entry for an event — tickets, season tickets and add-on tickets, with products optionally included. 100 per page.
  </Step>
  <Step title="Keep it current with incremental syncs">
    Pass `startTime` and you get only items modified since then, so a device on the gate can top up rather than re-downloading. Pass `includeZones` if your devices need to enforce zone rules locally.
  </Step>
  <Step title="Validate locally as attendees arrive">
    Your device decides. The platform is not consulted, so it cannot check live capacity or occupancy.
  </Step>
  <Step title="Upload the results in bulk">
    [Admit Entry Tickets](/api-reference/access-control/admit-entry-tickets) takes an array of scans. Each carries a `barcode`, `eventId`, `scannedOn` (UTC) and a `status` of `scanned` or `failed`, plus optional `zoneId`, `statusDetail`, `scan` direction, coordinates, gate and scanner.
  </Step>
</Steps>

Idempotency works at two levels. A `uuid` on the request makes a repeated upload return the previous response; a `uuid` per ticket skips an individual scan already recorded.

Use both — a batch upload is exactly the kind of call that gets retried.

<Warning>
Offline scanning cannot enforce anything that depends on live state — capacity limits, current occupancy, scan limits already consumed on another device, in/out state across devices.

Report accurate scan times in `scannedOn` so the attendance data is correct after the fact.
</Warning>

Upload refusals as well as admissions, with a `status` of `failed` and a `statusDetail`. A refused entry that never reaches the platform leaves no record, and refusals are usually what an investigation after the event needs to see.

## Getting the Data Your Layer Needs

| You need | Endpoint |
|----------|----------|
| Which events this device should be working with | [Retrieve Activated Events](/api-reference/events/retrieve-activated-events), [Activate Events](/api-reference/events/activate-events) |
| The event's zones and their live attendance statistics | [Retrieve Zones](/api-reference/zones/retrieve-zones), [Retrieve a single zone](/api-reference/zones/retrieve-a-single-zone) |
| Who is inside a zone, has visited, or has access | [Retrieve Zone Items](/api-reference/zones/retrieve-zone-items) |
| The tickets valid for entry | [Retrieve Entry Tickets](/api-reference/access-control/retrieve-entry-tickets) |
| What is on sale for an event | [Retrieve Sale Items](/api-reference/sale-items/retrieve-sale-items) |
| Configuration for the authenticated user | [Retrieve Application Config](/api-reference/app-configuration/retrieve-application-config) |

[Retrieve Zone Items](/api-reference/zones/retrieve-zone-items) is the one for an operations view rather than a gate. It searches within a zone by access, visited or currently inside — enough for a live occupancy dashboard, a "find this attendee" lookup, or an evacuation roll call.

## NFC and Secure Barcodes

**NFC.** Tags are paired to purchased tickets with [Pair NFC Ticket](/api-reference/access-control/pair-nfc-ticket), then presented as `nfcIds` on subsequent scans.

Pairing takes the ticket's barcode, the tag's identifier and the event; `pair-barcode-again` re-pairs a ticket that already has a tag. See [NFC Pairing](/core-platform/event-management/nfc-pairing).

**Secure barcodes.** Events using [secure barcodes](/core-platform/event-management/secure-barcodes) issue rotating, time-based codes rather than static ones, which stops a screenshot being shared.

If your scanning layer handles them, set `secure` on the scan so the record shows the code was verified. A scanner that falls back to the static barcode removes the protection the event was configured for — handle the rotating code, or route those events through the app.

## Guest Lists

Guest list attendance differs from ticketed entry: one entry can admit several people.

[Retrieve Guest List Attendees](/api-reference/access-control/retrieve-guest-list-attendees) fetches the guest lists for one or more events with their entries. [Update Guest List Attendees](/api-reference/access-control/update-guest-list-attendees) records how many people arrived against an entry. See [Guest Lists](/core-platform/sale-items/guest-lists).

## Admitting Without a Gate

[Admit Order Tickets](/api-reference/orders/admit-order-tickets) scans every ticket on an order into its event's entry zone in one call, including bundled tickets. Products and season tickets are ignored.

This is for when nobody is scanning anything — a hospitality arrival handled at a desk, a group checked in as a unit, a correction after the event.

It is not a substitute for a gate: it admits an order wholesale, without the per-item checks a real scan applies.

## Reacting to Scans From Elsewhere

If your system needs to *know about* admissions rather than perform them — a venue occupancy display, a hospitality system, an analytics pipeline — use [webhooks](/core-platform/technical/webhooks) rather than polling:

| Webhook | Fires when |
|---------|-----------|
| **Attendee check in** | An attendee is scanned into a zone or the main entry |
| **Attendee check out** | An attendee is scanned out — a zone, the default **Entry** zone, an [auto scan-out](/core-platform/event-management/access-control#auto-scan-out) time, or an out-direction scan through the API |

Check-out deliveries carry a `scans` array — company, event, zone, customer and item, plus `scannedAt` and `visitDuration` in seconds. Occupancy and dwell time come out of the webhook rather than being computed by polling. Full payloads in the [Webhook Reference](/webhook-reference).

Webhooks retry three times with exponential backoff and time out after 3 seconds, so acknowledge quickly and process asynchronously — a slow endpoint drops deliveries during the busiest period.

## Operational Practicalities

<AccordionGroup>

<Accordion title="Rate limits at the gate">
  Real-time scanning is one call per admission, so a busy gate generates a high sustained request rate. Establish your expected peak and get the limit raised in advance.

Have a degraded mode for when you reach it — falling back to offline validation keeps the gate moving. See [Getting Set Up](/integrate/getting-access#rate-limits).
</Accordion>

<Accordion title="Scope the token to scanning only">
  A scanning integration needs to read tickets and record scans, not refund orders or edit events — and a token on field hardware is more exposed than one on a server. Create a dedicated user with a minimal role. See [Roles & Permissions](/core-platform/system-access/roles-and-permissions).
</Accordion>

<Accordion title="Send times in UTC">
  `scannedOn` on a bulk upload must be UTC. Devices with local clocks, and devices crossing a DST boundary mid-event, are a common source of attendance data that reads incorrectly afterwards. See [Timezones](/core-platform/core/timezones).
</Accordion>

<Accordion title="Handle the all-or-nothing rule deliberately">
  Both `barcodes` and `nfcIds` accept several identifiers, and one refusal refuses the whole batch. For a group arriving together that is usually the intent. For a turnstile, send one identifier per call so a single invalid ticket does not turn away everybody behind it.
</Accordion>

<Accordion title="Reconcile afterwards">
  Attendance is reportable independently of your integration. The [attendance reports](/core-platform/reporting/default-reports) are the record of who came in, so reconcile your own data against them rather than against device logs — particularly after an event that ran partly offline.
</Accordion>

</AccordionGroup>
