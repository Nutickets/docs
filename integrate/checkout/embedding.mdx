## Overview

Embedding puts the shop inside a frame on your page. The customer selects items, checks out and pays without the page behind them changing.

There are four variations, built from the same script, settings object and URL parameters. Each adds something for you to maintain, so take the earliest one that meets the requirement.

The admin area's embed wizard generates working code for an event, which is the quickest way to get something running. It needs the **Website integration** feature active — see [Website Integration](/user-manual/technical/iframe-embeds).

## How the Embed Works

Two things go on your page: a script tag that loads the embed script from your shop, and a trigger element carrying a settings attribute.

```html
<button data-nu-settings="{base64}" data-nu-settings-version="2">
  Buy tickets
</button>
<script src="https://tickets.example.com/js/embed-script-1.0.js"></script>
```

On load, the script scans for elements carrying `data-nu-settings`, decodes the settings, and builds a frame for each one. Clicking the trigger reveals that frame.

The attribute value is the base64 of a URI-encoded JSON object; `data-nu-settings-version="2"` tells the script to decode it that way.

Once wired, the script removes the `data-nu-settings` attribute from the element and tracks the embed internally, so re-scanning the page will not create duplicates.

### The Settings Object

| Key | What it controls |
|-----|------------------|
| `eventUrl` | The shop URL the frame loads. This is where the URL parameters below go. |
| `allowedOrigin` | Your shop's origin. Messages arriving from anywhere else are ignored, and it is the target origin for commands you send in. |
| `showInModal` | `true` opens the frame as a modal overlay. `false` embeds it inline. |
| `iframeTarget` | A CSS selector for the element the inline frame is appended to. Only applies when `showInModal` is `false`. |
| `fullScreen` | Whether a modal frame fills the whole viewport or sits as a centred panel. |
| `height` | Height of a panelled modal frame, default `700`. `'auto'` lets the frame grow with its content instead of scrolling inside a fixed box. Ignored when `fullScreen` is `true`. |
| `modalOpacity` | Darkness of the backdrop behind a modal frame, `0`–`100`. |
| `autoLoad` | Opens the frame on page load rather than waiting for a click. |
| `companyTitle` | Used as the frame's accessible title. |

<Warning>
`allowedOrigin` is a security boundary, and the script enforces it strictly: a message is accepted only if it came from the frame it claims to and its origin matches exactly. Get it wrong and you receive no seat selections, tracking or basket expiry events — the script logs *Message source is not within allowed Origin* to the console rather than failing silently.

You can write it as a full URL; the script reduces it to an origin before comparing, so a trailing slash or path no longer breaks the match.
</Warning>

### The URL Parameters

Everything about what the frame *shows* is controlled by parameters on `eventUrl`, not by the settings object:

| Parameter | Effect |
|-----------|--------|
| `displayPurchaseItemsByDefault=1` | Land on the event's item selection step rather than its description. What the wizard now emits — it also sets `=0` when the option is off |
| `showItems=1` | The same, for one visit only. Use this where you do not want the choice remembered |
| `iframeMenu=1` | Show the shop's site navigation inside the frame |
| `hideLogout=1` | Remove the sign-out option from the embedded view |
| `hideIframeClose=1` | Remove the frame's own close button |
| `access_code`, `discount_code`, `language`, `currency` | As for any shop link — see [Linking to the Shop](/integrate/checkout/linking-out#carry-state-in-the-link) |

The wizard sets `hideIframeClose=0` for modal embeds and `hideIframeClose=1` for inline ones, on the reasoning that a modal needs a way out and an inline frame is already part of your page. [Shop URL Parameters](/integrate/reference/url-parameters) is the complete reference.

## Variation 1: The Stock Modal

The default, and what the wizard generates: `showInModal: true`, a full-screen or panelled overlay, `displayPurchaseItemsByDefault=1` on the URL. The customer clicks your button, picks items, checks out, pays and sees their confirmation, all inside the frame.

Nothing crosses the boundary except the messages the shop chooses to send. Your page listens for those to know when to close or reset the frame, and to feed the customer journey into your own analytics:

```js
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://tickets.example.com') return;
  if (!event.data?.nuMessage) return;

  if (event.data.close) {
    // The customer finished, or asked to leave
  }
  if (event.data.event === 'expire') {
    // Their basket timed out — reset the frame
  }
  if (event.data.nuTracker) {
    // A trackable customer action
  }
});
```

Every message the shop sends carries `nuMessage: true`. Check for it before reading anything else — a page of any size receives messages from scripts that have nothing to do with the embed, and the marker is what separates ours from theirs.

The generated script handles `close` and `visit` for you — you only need your own listener for tracking and basket expiry.

[Embed Messages](/user-manual/technical/embed-messages) documents every message and parameter, which customer data is included, and how cookie consent affects what is sent.

<Note>
A `close` message means the embed *should* close — it does not close anything by itself if you are handling messages yourself.

Destroy the frame or reload it to its starting URL so the next customer starts clean. The script's `nuCloseModal()` does exactly that, and takes the embed's hash to act on one frame — `nuCloseModal(hash)` — leaving any other embeds on the page alone.
</Note>

### Things That Have to Leave the Frame

Some steps cannot complete inside an embedded frame, and the shop breaks out rather than failing:

| Situation | What happens |
|-----------|--------------|
| A payment page that must render top-level | Opens in a new tab, and the shop sends `close` after a short delay so the tab is not blocked |
| A social sign-in | Same — new tab, then `close` |
| The **X** share option on an event | Sent as a `visit` message for your page to follow |
| Sending the customer to an external identity provider | A full-page journey, so the customer is lifted out and returned. To avoid it, [pre-authenticate the frame](/integrate/identity/pre-authentication) instead |

The delay on the first two exists because some browsers block a new tab if the frame closes immediately. If you are handling `close` yourself, do not race it.

## Variation 2: Inline Rather Than Modal

Set `showInModal: false` and give `iframeTarget` a selector, and the frame is appended into that element instead of overlaying the page.

The script hides the trigger and clicks it for you, so the frame loads with the page — there is no button for the customer to find.

```json
{
  "eventUrl": "https://tickets.example.com/events/48213?displayPurchaseItemsByDefault=1&hideIframeClose=1",
  "allowedOrigin": "https://tickets.example.com",
  "showInModal": false,
  "iframeTarget": "#ticket-shop"
}
```

Use this when the shop is the content of the page rather than an interruption — a dedicated **Tickets** page, or a panel in a layout of your own.

You own the container's dimensions, so give it a sensible height: the frame fills what you provide.

## Variation 3: Splitting the Journey Across Your Own Pages

Reach for this when the stock modal carries the customer further than you want it to.

Item selection happens in a modal on your event page. When the customer is ready to check out, you intercept and take them to a page of your own, with a second frame loading the shop's basket or checkout.

You get your own page furniture around the checkout, and room to insert steps of your own — membership prompts, upsells of your own products, terms you have to present before payment.

On your side this is two pages, each with its own embed, pointed at different shop URLs.

To know when the customer is ready to move on, listen for `seatSelected` and `GASelected` and use them to enable your own **Continue** action.

<Note>
Your code is what moves the customer between pages, so carrying the basket across that step is yours to build. [Carrying the Basket Across Pages](/integrate/checkout/session-continuity) covers the two ways to do it.
</Note>

## Variation 4: Embedding One Component

You do not have to embed a whole shop page. Point `eventUrl` at `/events/{id}/seating-plan` and only the [seating plan](/user-manual/seating-plans/introduction) loads.

This is the most common single-component embed: your page owns everything else, and the frame gives you a live seat map with real availability.

Seating plans are the one part of the embed that talks in both directions. The plan sends selection events out, and accepts commands in — highlighting areas, selecting seats, switching between seat-level and price-band selection:

| Direction | Examples |
|-----------|----------|
| Plan → your page | `planReady`, `seatSelected`, `seatUnselected`, `GASelected`, `GAUnselected`, `error` |
| Your page → plan | `selectSeat`, `unselectSeat`, `focusArea`, `enterArea`, `setGa`, `focusPriceBand`, `setHighlightMode` |

Loaded through the generated script, the outbound messages are re-dispatched on your page as DOM events of the same names (`seatingError` for errors). The script's `postToIframe` helper sends commands the other way, addressed to your configured `allowedOrigin`.

Wait for `planReady` before sending anything. Full list in [Embed Messages](/user-manual/technical/embed-messages#seating-plan-messages).

What you do with those selections is the subject of [Building Baskets with the API](/integrate/checkout/building-baskets) — the plan reports what the customer picked, but it does not create a basket.

<Note>
Seat and area selection events only ever come from a seat map or general-admission selection screen. Embedding a plain event page and expecting `seatSelected` will get you nothing — point the frame at the seating plan URL.
</Note>

## Practical Details

<AccordionGroup>

<Accordion title="Adding embeds after page load">
  The script scans for `[data-nu-settings]` when the document becomes ready. If you render triggers later — a single-page app, a filtered listing, a modal of your own — call `window.nuModalInit()` to scan again. It only wires elements it has not already seen, so repeated calls are safe.

  If you are rebuilding the settings as the customer changes something (picking a different event, say), debounce the re-scan rather than calling it on every keystroke: each distinct settings value produces its own frame.
</Accordion>

<Accordion title="Several embeds on one page">
  Each trigger gets its own frame and its own settings, so a listing page with a **Buy** button per event works without special handling. All of them share one message listener, and each message is matched back to its frame by the window it arrived from — so a `close` from one embed closes that embed and leaves the rest open.

  The frame chrome flags — `iframeMenu`, `hideLogout`, `hideIframeClose`, `hideHome` — are remembered per frame rather than per shop, so setting one on a single embed no longer changes the others on the same page.
</Accordion>

<Accordion title="Closing a frame that has no close button of its own">
  Some embedded pages — the seating plan among them — have no close control, and an inline embed with `hideIframeClose=1` deliberately has none either. If you need your own close affordance, call the script's `nuCloseModal()` directly rather than waiting for the frame to send `close`.

  Pass the embed's hash to close just that one. Called with no argument it closes and resets every embed on the page, which is what you want for a single-embed page and rarely what you want otherwise.

  A modal frame covers the viewport at a high stack order, so a close button of your own has to sit above it. An ordinary in-flow button will be underneath and unclickable while the modal is open.
</Accordion>

<Accordion title="Building the iframe yourself">
  You can skip the script and write your own `<iframe>`, but the message plumbing becomes yours to build, and there are two things to get right.

  **Tell the shop your origin.** On load the frame posts `{ nuRequestHandshake: true }`. Reply to it and the shop takes your origin from the reply itself, which is the most reliable route because the browser attests it. If you would rather not answer, add `parent-origin` set to your site's origin to the frame URL instead. Do neither and the shop falls back to the referring page, which browsers do not always send: `close` and `visit` are broadcast and still arrive, but tracking, basket expiry, seating plan messages and the session identifier do not.

  **Give the frame a `name`.** The chrome flags and the display mode are remembered against it, so two unnamed frames on one page share one set of remembered settings and overwrite each other. The generated script names every frame it creates; a hand-built frame without one logs a warning to the console.
</Accordion>

<Accordion title="Frame height and scrollbars">
  Shop pages fill at least the height of the frame, so a short page — a sold-out event, a thin listing — puts its footer at the bottom rather than leaving the frame scrolling over empty space.

  That settles the height of the content. The height of the *frame* is still yours: an inline embed fills the container you give it, and a panelled modal uses `height`, `700` by default. Where the content varies enough that no single figure fits, `height: 'auto'` lets the modal grow with it instead of scrolling inside a fixed box.
</Accordion>

<Accordion title="Frame permissions">
  The generated frame is sandboxed and carries `allow="payment"`, which is what lets payment request flows work inside it. If you are building the frame yourself and payment appears to do nothing, check that first.
</Accordion>

<Accordion title="Embedding the account area">
  The account pages under `/account` embed like any other shop page, so you can offer order history, ticket downloads and profile editing inside your own pages.

  Two things to plan for. The customer has to be signed in, which in a frame means [pre-authentication](/integrate/identity/pre-authentication) rather than a redirect. And if your site already has its own account area, the [customers API](/api-reference/customers/retrieve-customers) may fit better than embedding ours.

  See [Customer Accounts](/user-manual/ticket-shop/customer-accounts) for what the account area contains.
</Accordion>

</AccordionGroup>

## Tracking From the Host Page

Tag managers and tracking pixels are unreliable inside a frame, because browsers restrict the cross-site storage they depend on. Scripts loaded within the embed may not fire every event, or may fail to initialise at all.

Instead, run tracking on your own domain and your own page, driven by the messages the shop sends.

Every trackable action is posted out — page views, item impressions, add to basket, checkout steps, purchase, errors — in a Google Analytics shape and, where pixels are configured, an ad-platform shape.

The wizard can generate a ready-made listener for you: **Add cross-site tracking script** on the modal settings step appends it to your embed code, and it is on by default if the company has a Google Tag Manager code configured.

<Warning>
Google Analytics shaped tracking messages reach your page **regardless of the customer's cookie choice in the shop**. The shop honours that choice for its own tracking; your page receives the data either way and must apply consent before passing anything on.

Email addresses and phone numbers are hashed before they leave the shop. Names, customer identifiers and city are not — treat these messages as personal data. See [Embed Messages](/user-manual/technical/embed-messages#what-customer-data-is-included).
</Warning>
